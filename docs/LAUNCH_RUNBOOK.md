## القاعدة السارية (قرار المالك)

### بوّابة التحديث الأمني — 2026-10-21

- لا تُحدّث حزم خدمة Windows الحيّة مباشرةً: أنشئ بيئة Python 3.11 منفصلة،
  ثبّت `requirements.txt` مع `security-constraints.txt` المرافق، واختبر نسخة
  من القاعدة أولاً. انتقل Django من 4.2 إلى 5.2؛ افحص المهاجرات قبل تبديل الخدمة.
- أوامر التحقق في البيئة الجديدة:
  ```powershell
  python -m pip install --upgrade pip setuptools -c security-constraints.txt
  python -m pip install -r requirements.txt
  python -m pip check
  $env:PYTHONIOENCODING="utf-8"
  python manage.py test core.tests_security core.tests_audit core.tests_restore_archive core.tests_legacy_restore core.tests_media_protection --settings=lettersys.settings_test
  python manage.py check
  python manage.py migrate --plan
  ```
  افحص الخطة على نسخة القاعدة لا البيانات الحيّة، وشغّل اختبارات البريد والمرفقات
  والاستخراج قبل التبديل. احتفظ بالبيئة والنسخة الاحتياطية السابقة للرجوع.
- ملف القيود يرفع الحدود الدنيا للحزم المتأثرة، ولا يثبّت الحزم الاختيارية
  أو أدوات التطوير بمفرده. افحص أيضًا أي حزم إضافية موجودة على الخادم.
- محدّد الدخول وسجل التدقيق يستخدمان سياسة IP نفسها: `REMOTE_ADDR` افتراضيًا.
  خلف وكيل موثوق يمكن تفعيل `TRUST_X_FORWARDED_FOR=True` **فقط** مع منع الوصول
  المباشر وقيام الحافة باستبدال الترويسة الواردة بقيمة محسوبة موثوقة، لا إلحاقها.
  مثال Nginx لحافة واحدة: `proxy_set_header X-Forwarded-For $remote_addr;`.
  لا تستخدم `$proxy_add_x_forwarded_for` مع هذه الثقة إن كان أول عنصر من العميل؛
  مع سلسلة وكلاء يلزم تقنين السلسلة عند الحافة قبل تمكين الثقة.
- الاستعادة من ZIP وTAR.GZ/TGZ تقبل ملفات عادية ومجلدات فقط: لا مسارات خارجة،
  ولا روابط، ولا أسماء أجهزة أو مسارات Windows البديلة. الحد 10,000 عضو
  و64 GiB إجمالاً، وبحد أقصى المساحة الحرة ناقص 128 MiB. عند الرفض تظهر رسالة
  وتُسجّل الواقعة وتُنظّف المستخرجات. للنسخ الأكبر استخرج BAK بأداة موثوقة
  على الخادم ثم استخدم مساره المباشر.
- فك 7z الآلي معطّل بقرار المالك؛ استخرج BAK يدويًا ثم استعده. النسخ غير المضغوطة
  لا تمرّ بمسار استخراج الأرشيف.
- حُذف اعتماد `PyPDF2` المهجور وغير المستخدم؛ معالجة PDF تستخدم `pypdf`.
  عند ترقية بيئة قديمة أزل `PyPDF2` صراحةً، فتثبيت المتطلبات لا يزيل الحزم الزائدة.
- هوية متصفح الحجوزات تقرأ التوقيع عبر `HttpRequest.get_signed_cookie`، لا بتركيب
  salt يدوي. هذا يطابق كتابة Django للتوقيع بعد التحديث ويحافظ على سياسته
  المعلنة لقبول التواقيع السابقة؛ لا تُعد القراءة إلى افتراض صيغة إصدار قديم.
- تدقيق البيئة المعزولة كشف `CVE-2026-106454` في Twisted، بلا إصدار إصلاح
  معلن في نتيجة التدقيق. يخص خادم IMAP في `twisted.mail.imap4`، لا عميل
  `imaplib` المستخدم هنا. لم يظهر مسار يستدعيه في التطبيق؛ هذا ليس إصلاحًا
  للحزمة ولا ضمانًا لسلامة كل استخداماتها. تابع إصدار الإصلاح وأعد التدقيق؛
  لا تُشغّل خادم IMAP من Twisted اعتمادًا على هذا التقييم.

| الحالة | ما يُخزَّن | ما يُعرض |

## عتادُ النموذج — ما لا ينتقل بـgit

**تغيّر هذا في 2026-09-01**: صار المستودعُ **خاصّاً**، وعتادُ التشغيل يُشحَن
معه — الأوزانُ عبر **Git LFS** والبصماتُ النصّيّةُ في git عاديّ. فالاستنساخُ
يعطي نسخةً عاملة، لا نسخةً عمياءَ تبدو سليمة.

القاعدةُ العامّة تبقى «`var/` خارج git»؛ المستثنى **ما يفحصه عقدُ العتاد**
(`core/extraction/artifacts.py`) وحدَه. وما زال خارجاً عمداً: النماذجُ الميّتة
(`*_rollback`/`*_backup`)، ومخرجاتُ التدريب، و**`.encryption_key`** — سرٌّ
يُنسَخ يدويّاً ولا يدخل مستودعاً أبداً.

| الملفّ | الأثرُ عند الغياب |
|---|---|
| `var/models/number_detector.onnx` | لا صندوقَ عددٍ ولا تاريخ ⟵ المسارُ البصريُّ كلُّه صامت |
| `var/models/handwritten_digits_crnn.onnx` | لا قراءةَ عددٍ يدويّ |
| `var/models/handwritten_dates_crnn.onnx` | لا اقتراحَ تاريخ |
| `var/models/handwritten_dates_charset.json` | **أخطرُها**: النموذجُ يعمل والطقمُ ناقصٌ «/» ⟵ فكُّ الترميز يرفع `IndexError` فيسقط الاقتراحُ صامتاً |
| `var/entity_*.json` · `var/handwriting_layout_priors.json` | ترجيحُ نوع الوثيقة ومطابقةُ الجهة يضعفان |
| `.encryption_key` | يُسَكُّ مفتاحٌ جديدٌ بلا صوت ⟵ كلماتُ مرور البريد المخزّنة لا تُفكّ |

وثلاثةٌ خارج المستودع لا تقلّ لزوماً: **حزمة `onnxruntime`** (كانت غائبةً عن
`requirements.txt` حتّى 2026-09-01 — أيُّ نسخةٍ مبنيّةٍ قبلها بلا قراءةٍ يدويّةٍ
إطلاقاً)، ومحرّك **tesseract**، وبياناتُ لغته (`ara`+`eng`).

```powershell
# على نسخةٍ جديدة: اسحب الأوزان (LFS) ثمّ انسخ المفتاح ثمّ تحقّق
git lfs install
git lfs pull
copy \<مسار-آمن>\.encryption_key .          # لا يأتي مع المستودع عمداً
python manage.py models_healthcheck --strict --load --hash
```

> إن نُسي `git lfs pull` فالملفّاتُ موجودةٌ بأسمائها لكنّها **مؤشّراتٌ نصّيّةٌ
> من ثلاثة أسطر** — والفحصُ يمسكها: `--load` يفشل بفتح ONNX، وبلا `--load`
> يمسكها فحصُ الحجم (بضعةُ بايتاتٍ لا ميغابايتات).

**المساراتُ مثبَّتةٌ على جذر المشروع** منذ 2026-09-01 (`core/extraction/artifacts.py`)
فلا يعود يهمّ من أين تُقلَع الخدمة؛ وقبل ذلك كانت ستّةٌ منها نسبيّةً لمجلّد العمل
وكان الإقلاعُ من مجلّدٍ آخر **يُسقط الاستخراجَ كلَّه** لا القراءةَ اليدويّة وحدها.

## بوابة توافق القاعدة — إصلاح 2026-10-12، الدفعة الأولى

قبل السماح بالكتابة بعد نشر أي إصدار:

```powershell
$env:PYTHONIOENCODING="utf-8"
& ".\.venv\Scripts\python.exe" manage.py db_healthcheck --strict
```

الأمر موجود في المشروع: يفشل عند وجود ترحيلات معلقة أو انحراف النماذج أو
أسرار غير مشفرة. لا تستخدم `--fake` لإخفاء أعمدة غير موجودة.

للتحقق من الترحيلات والقيود على PostgreSQL، مع إبقاء مجموعة SQLite المعتادة:

```powershell
$env:PYTHONIOENCODING="utf-8"
$env:LETTERSYS_PG_TEST_DB="test_lettersys_upgrade_local"
& ".\.venv\Scripts\python.exe" manage.py test core.tests_database_upgrade core.tests_reservation_ttl core.tests_registration core.tests_numbering_per_dept core.tests_book_scope --settings=lettersys.settings_test_postgresql
```

**قاعدة الاسم أعلاه مؤقتة وقابلة للحذف بالكامل بواسطة مشغل الاختبارات**؛ لا تسمّ
بها قاعدة تريد الاحتفاظ بها. الإعداد يرفض الاسم الغائب أو غير المطابق أو اسم
قاعدة التشغيل. يحتاج الدور إلى `CREATEDB` للاختبارات فقط؛ ليس سبباً لمنحها
لحساب تشغيل الإنتاج.

**ترقية 0079 إلى 0083:** أوقف Django والعمال والمسح وكل مصادر الكتابة؛ أنشئ
نسخة مشفرة واستعدها إلى قاعدة منفصلة، وقارن بصمات البيانات قبل ترحيلها. اختبر
الترحيلات هناك أولاً، ثم أعد مقارنة المصدر بالنسخة قبل ترحيل المصدر نفسه.
0080 يربط الحجوزات بالأقسام وينهي الحجوزات الحية غير المرتبطة بكتاب، و0081
ينقل التكرار الحي إلى فترة السماح، و0082 يجعل التفرد بحسب `client_key`.
هذه تغييرات بيانات مقصودة، وليست ترقية أعمدة فقط.

**الرجوع ليس مضموناً عبر `migrate` وحده:** تنظيف 0081 لا يستعيد القيم القديمة؛
والرجوع من 0082 إلى 0081 قد يفشل بقيد التفرد إذا وُجد حجزان حيان للمتصفحَين
في القسم نفسه. لا تعالج الفشل بحذف الحجوزات أو تعديل الترحيلات التاريخية.
عند الحاجة، استعد النسخة السابقة إلى قاعدة جديدة مع إصدار الكود الموافق
لها، وراجع أثر أي كتابة حدثت بعد الترقية قبل تبديل الاتصال.

في تنفيذ الدفعة الأولى طابقت بصمات بيانات 65 جدولاً بعد الاستعادة. بعد الترقية
بقيت بيانات 63 جدولاً كما هي؛ التغيير اقتصر على الحجوزات وسجل الترحيلات.
نجحت المجموعة المستهدفة: 75 اختباراً على PostgreSQL، وعلى SQLite نجح 71
اختباراً وتُجاوزت أربعة اختبارات خاصة بـPostgreSQL. نجح الفحص الصارم على
القاعدة المتصلة؛ بقي 13,108 كتب و23 حجزاً دون حذف، وأزيلت قاعدة تجربة
الاستعادة وحدها بعد التحقق مع إبقاء النسخة المشفرة.
إصلاحات تزامن المرفقات والعهدة والإحالات والفهارس دفعات مستقلة لم تُنفّذ هنا.

## النشرُ التلقائيّ — كلُّ دفعٍ إلى main

`.github/workflows/deploy.yml` يتّصل بالخادم عبر ssh ويشغّل `lettersys-deploy`.
لا يعمل حتّى تُضبط **أربعةُ أسرارٍ** في إعدادات المستودع؛ وبدونها يسقط السيرُ
برسالةٍ تُسمّي الناقص بالضبط (لا برسالة `ssh` عمياء).

```bash
gh secret set DEPLOY_HOST  --repo Abdulrahman-9/lettersys_project   # العنوان أو IP
gh secret set DEPLOY_USER  --repo Abdulrahman-9/lettersys_project   # مالكُ lettersys-deploy
ssh-keyscan -H <العنوان> | gh secret set DEPLOY_KNOWN_HOSTS --repo Abdulrahman-9/lettersys_project
# DEPLOY_SSH_KEY مضبوطٌ منذ 2026-09-01 (مفتاحُ نشرٍ ed25519 مُولَّدٌ لهذا الغرض،
# خاصُّه في أسرار GitHub وحدها). المطلوبُ على الخادم سطرٌ واحد:
#   echo 'ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIACWfXpnaUmwnSTCiwNnHoZXs3QbOwErqotyzPaT2c79 github-actions@lettersys-deploy' >> ~/.ssh/authorized_keys
```

**البياناتُ قبل الأوزان** (إنتاج 2026-09-01): قاعدةٌ فارغةٌ = **صفرُ جهاتٍ بنيويّاً** مهما
كانت الأوزانُ حاضرة — `Entity` و`LetterheadMemory` هما ما يُطابَق عليه. حمّل النسخةَ
الحقيقيّة (`pg_restore`) ثمّ **أعد تشغيل الخدمة**، و`models_healthcheck` يطبع أعدادَ الكتب
والجهات والذاكرة ويصرخ عند الصفر.

**ما يجب أن يفعله `lettersys-deploy` بعد كلّ سحب**: `git lfs pull` ثمّ `migrate`
ثمّ `collectstatic` ثمّ إعادةُ تشغيل الخدمة — و`models_healthcheck --strict`
بوّابةً قبل الإقلاع. ولا `makemigrations` في الإنتاج أبداً: توليدُ ترحيلٍ على
قاعدةٍ حيّة بابُ تلفٍ لا إصلاح.

**وبعد إصدار شهادة TLS**: احذف `SESSION_COOKIE_SECURE` و`CSRF_COOKIE_SECURE`
و`SECURE_SSL_REDIRECT` من `.env` — لا تجعلها `True` يدويّاً. الافتراضُ في
الشيفرة آمنٌ أصلاً، والحذفُ يعيدك إليه بلا سطرٍ منسيٍّ يرخي الأمانَ لاحقاً.
