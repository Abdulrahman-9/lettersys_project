## 1. الحكم التنفيذي

الصفحتان **صالحتان وظيفياً لكنهما هشّتان بنيوياً**: بنية «صفحة واحدة بوضعين» سليمة كمبدأ، لكن تنفيذ وضع التعديل عبر **monkey-patch لدوال الـ prototype داخل سكربت القالب** ولّد ازدواجاً وكذباً في العقود يكسر ثقة المستخدم والمطوّر معاً. أخطر ثلاث مشاكل، كلها **مؤكَّدة بالكود**:

1. **فقدان بيانات صامت (حرج):** بدء المسح ينفّذ `window.location.href = ud.redirect` (`extraction_smart.js:1619`) فيعيد تحميل الصفحة كاملةً ويمحو كل ما أدخله المستخدم قبل المسح — بلا تحذير، بينما الرفع اليدوي يبقى في الصفحة.
2. **استبدال-الكل من تدوير صفحة (حرج):** `update_book_api` عند وجود ملف ينفّذ `book.attachments.filter(is_deleted=False).update(is_deleted=True)` لكل المرفقات ثم `create_attachment` واحد (`books_api.py:738-740`) — فتدوير صفحة واحدة يؤرشف كل مرفقات الكتاب. مخالف لعقد الحفظ للتدقيق في نظام مراسلات رسمي.
3. **مؤشّر تحقّق كاذب + «مسح المزيد» وعد كاذب (عالٍ):** «✓ جاهز للحفظ (5/5)» يُفعّل الزر ثم يُرفض الحفظ لنوع مستند ناقص؛ وزر «مسح المزيد» ومنطق الدمج العميلي **ميت** في مسار الماسح الوحيد المدعوم.

**الحكم:** يحتاج توحيد الحفظ + مصدر حقيقة واحد للمرفق + فعل مسح صادق قبل أي توسعة. لا توسعة على أساس هشّ.

## 1.ب — ملاحظة المالك المؤكَّدة: زرّا الحذف المتناقضان (تحقّق مباشر)

الشكوى: «عند المسح والتراجع بحذف الصورة تبقى المعلومات المستخرجة». **السبب الجذري مؤكَّد بالكود** — يوجد زرّا حذف بسلوكين مختلفين:

| الزر | السلوك | الموضع |
|---|---|---|
| «مسح الملف» (`clearFile` / `clearFileFromModal`) | `clearFile()` **ثم** `clearForm()` → يمسح الصورة **والحقول** | `extraction_smart.js:1091-1096` |
| «حذف الممسوح» (`clearScannedButton` → `clearScannedFile()`) | `clearFile()` **فقط** بلا `clearForm()` → يمسح الصورة **ويُبقي الحقول المستخرَجة** | `extraction_smart.js:2257-2264` |

فالعلّة ليست «نقص زر» بل **تفريعة نسيت تفريغ النموذج**، فتبقى بيانات «مستخرَجة» بلا مصدر. الحل قرار منتج (انظر §7 P0).

## 3. تشريح منطق المسح والدمج والإرفاق

### كيف يعمل فعلاً اليوم
- **ثلاثة مداخل، نقطة التقاء واحدة:** المسح (NAPS2)، الرفع اليدوي، و`scan_token` في الـURL — كلها تلتقي عند `scan_process_upload` (`scan_settings.py:354`) الذي يوحّد كل شيء إلى **PDF واحد** ويخزّن token في الكاش.
- **الدمج متعدد الصفحات يقع خادمياً/جهازياً لا عميلياً:** NAPS2 يُخرج PDF واحداً من ADF؛ الخادم يبقيه واحداً. الدمج العميلي (`_mergeScannedImages`) **مسار ميت**.
- **وضع الإدخال:** `currentFile` (PDF مُجهَّز بـ token) → `save_book_api` → `create_attachment` كمرفق واحد جديد.
- **وضع التعديل:** سطح المسح/الرفع مخفي؛ المرفقات عبر `DocumentManager` حصراً. عند الحفظ لا يُرسَل ملف إلا إذا `_pagesEditedInPreview` صحيح — وحينها **استبدال كامل**.
- **ثلاثة مطابخ دمج/استبدال خلفية متعارضة الدلالة (مؤكَّد):**
  1. `SmartMergeService.merge_files` (`merge_service.py:84`) — غير هدّام، يُنشئ `AttachmentVersion` — يستدعيه **فقط** `AttachmentMergeViewSet` (`merge_api.py:39`) وهو **يتيم من الواجهة**.
  2. `attachment_merge_pages` (`attachments.py:222`, pypdf) — **الحيّ فعلاً** عبر `attachment/<pk>/merge/` — يكتب فوق `att.file`.
  3. `update_book_api` (`books_api.py:738`) — **استبدال-الكل**.

### لماذا هو غامض
- المستخدم لا يملك نموذجاً ذهنياً: لا تمييز لفظي/بصري بين «مسح / مسح المزيد / مسح جديد / مسح يستبدل».
- الأزرار **تكذب**: «مسح المزيد» غير موجود؛ الدمج «أعمى» بلا معاينة ترتيب؛ المسح يمحو الحقول؛ وحذف الصورة يُبقيها (§1.ب).
- **«الاستخراج الذكي» لا يستخرج فعلاً:** `SCAN_AUTO_OCR=False` افتراضياً (`scan_settings.py:432-453`) — كل مسح ينتهي بإدخال يدوي وبانر غامض.
- ثلاثة مطابخ دمج بدلالات مختلفة (نسخة / كتابة فوقية / استبدال) بلا مصدر حقيقة واحد.

### التدفّق البديل المقترح (نمط Mayan/ELO/DocuWare: file-vs-version + tray + أفعال مسمّاة-بالنيّة)
1. **فعل مسح واحد صادق:** «مسح من السكانر» يستقبل `ud.token` ويستدعي `loadScannedFile` **محلياً** — بلا `window.location.href`، بلا فقدان بيانات، بلا تباين استخراج.
2. **منطقة تجهيز (staging) قبل الالتزام:** كل مسح/رفع يُرتَّب في شبكة مصغّرات (موجودة أصلاً `js:2151-2219`) قابلة للسحب قبل الالتزام بالكتاب.
3. **أفعال مسمّاة-بالنيّة:** بعد أول مسح: «+ مسح صفحة أخرى (تُلحَق)» مقابل «مسح مستند جديد (يستبدل)» بتأكيد صريح (نمط Epson «Add Page» / ScanSnap Continuous).
4. **إدراج بموضع صريح:** عبر `scan_edit_page` op جديد `insert-at` (`doc.insert_pdf(start_at=idx)` بـ fitz) — يقتل «gymnastics» الحذف+الدمج.
5. **مصدر حقيقة واحد للمرفق:** كل تعديل يستهدف `attachment_id` محدّداً ويُنتج `AttachmentVersion` — الأصل يُحفظ دائماً، لا أرشفة أشقّاء.
6. **مطبخ دمج واحد:** توحيد على `attachment_merge_pages` وحذف `SmartMergeService`+`merge_api`+`AttachmentMergeViewSet` (يتيمة)، مع إظهار ترتيب الدمج كمصغّرات قابلة للسحب.

| «حذف صفحات» في DocumentManager | `_prompt` نصّي خام «1,3-5» بينما شبكة المصغّرات البصرية موجودة أصلاً. |

### تخطيط أزرار مقترح (وضع التعديل)
```
┌─────────────────────────────────────────────────────────────┐
│  [مؤشّر: كل الحقول مكتملة ✓]        [عودة]   [✓ حفظ التعديلات] │
└─────────────────────────────────────────────────────────────┘
```
- **إخفاء خادمي** لـ `extractButton` و`.scan-action-bar` بـ `{% if edit_book_json != 'null' %}` — لا JS، لا وميض، لا فجوة.
- **«حفظ التعديلات»** الأبرز: لون ممتلئ + وزن أعلى (الفعل الأساسي).
- **«عودة»** ثانوي محايد (رمادي/شفاف) — لا أحمر تدميري؛ الأحمر يُحجَز للحذف الحقيقي فقط.
- **إعادة توزيع الشريط** لإزالة فجوة الزر المخفي.
- **تعديل الصفحات** كله عبر `DocumentManager`/شبكة مصغّرات واحدة (زر «تحرير الصفحات») — إزالة أدوات المعاينة التحريرية من وضع التعديل، ما يلغي `_pagesEditedInPreview` ومسار الإرسال المشروط كلياً.

## 5. المراجعة التصميمية البصرية (كلا الوضعين) — [مصدرها الرئيس/المستطلعون، لا عدسة مخصّصة]

- **التسلسل الهرمي:** في التعديل ينكسر — زرّان متساويان بصرياً بلا فعل أساسي واضح. في الإدخال شريط الإجراءات سليم (n/5) لكن يعِد بما لا يفي.
- **RTL:** التخطيط العربي ثنائي العمود عبر Grid سليم؛ لا مشاكل اتجاهية مرصودة.
- **اللون:** إساءة استخدام الأحمر التدميري لزر الإلغاء/العودة (دلالة خاطئة). دلالة اللون يجب أن تعكس الخطورة لا مجرد التمييز.
- **الكثافة:** DocumentManager يكدّس حتى 5 أزرار لكل مرفق — يخالف حدّ NN/g (≤7 أفعال مرئية). الحل: split-button + قائمة overflow/سياق للأفعال الثانوية.
- **الحالات الفارغة:** شبكة المصغّرات تُخفى للمستند أحادي الصفحة (`js:2154`) — فلا مرساة لعمليات الصفحة في الحالة الأشيع بالمراسلات. أظهرها دائماً عند وجود `previewToken`.
- **تسريب حالة قديمة:** `qualityHero`/`needsReviewCard` لا تُخفيان في `smartClearAndStay` — تبقى فوق نموذج فارغ في دورة التسجيل المتتالية.
- **الوميض:** إخفاء أزرار التعديل بـ JS مؤجَّل — يجب أن يكون خادمياً.
